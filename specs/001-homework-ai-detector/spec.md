# Feature Specification: Homework AI Detector

**Feature Branch**: `001-homework-ai-detector`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "Выполнить задачу из docs/architecture.md — модуль детекции AI-генерации кода в решениях домашних заданий (Homework AI Detector)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Базовый анализ репозитория с решением (Priority: P1)

Преподаватель или куратор курса получает ссылку на GitHub-репозиторий со студенческим решением домашнего задания. Он вводит текст критериев задания и ссылку на репозиторий. Система скачивает репозиторий локально, извлекает полную историю коммитов и весь исходный код, после чего локальная LLM выносит структурированный вердикт по системе «Светофор»: вероятность того, что решение сгенерировано ИИ.

**Why this priority**: Это ядро ценности фичи. Без этого сценария модуль не решает ни одну задачу. Именно он дает преподавателю быстрый, аргументированный сигнал (зеленый/желтый/красный) вместо визуального ревью чужого кода.

**Independent Test**: Полностью тестируется independently: на вход подаются критерии задания (строка) и URL публичного репозитория, на выход — структурированный вердикт (статус, уверенность, обоснование, списки признаков). Доставляет ценность сам по себе: преподаватель получает готовое заключение по одному репозиторию.

**Acceptance Scenarios**:

1. **Given** текст критериев задания и URL публичного репозитория с решением, **When** запущен анализ, **Then** система возвращает вердикт со статусом `green`, `yellow` или `red`, уверенностью от 0.0 до 1.0, обоснованием на русском языке и списками признаков AI- и человеческой генерации.
2. **Given** репозиторий с постепенной историей коммитов, осмысленными сообщениями и специфичными для задачи именами, **When** запущен анализ, **Then** вердикт отражает статус «человек» (green) с обоснованием, ссылающимся на конкретные признаки (история коммитов, имена, соответствие критериям).
3. **Given** репозиторий с единственным коммитом («initial commit»), бездушной структурой и артефактами нейросети в коде («Конечно, вот ваш код», «Sure, here is the solution»), **When** запущен анализ, **Then** вердикт отражает статус «явный ИИ/копипаст» (red) со списком конкретных обнаруженных признаков.
4. **Given** репозиторий с качественным кодом, но подозрительной историей (1–2 коммита с разницей в минуту) и «водянистыми» комментариями в стиле ИИ при признаках ручной адаптации, **When** запущен анализ, **Then** вердикт отражает статус «смешанный/подозрительный» (yellow) с указанием противоречивых признаков в обоих списках.

### User Story 2 - Анализ приватного репозитория (Priority: P2)

Некоторые студенты размещают решения в приватных репозиториях. Преподаватель должен иметь возможность проанализировать такое решение, предоставив систему со служебным токеном доступа, хранящимся во внешней (не в коде) конфигурации окружения.

**Why this priority**: Расширяет применимость фичи на реальные учебные процессы, где приватные репозитории распространены, но не является обязательной для минимально жизнеспособной версии — публичных репозиториев достаточно для MVP.

**Independent Test**: Тестируется independently: задается URL приватного репозитория, токен доступа выставляется в переменную окружения, после чего анализ возвращается корректный вердикт. Отдельно проверяется, что при отсутствии токена система возвращает понятную ошибку, а не «падает» молча.

**Acceptance Scenarios**:

1. **Given** URL приватного репозитория и токен, выставленный в переменную окружения, **When** запущен анализ, **Then** репозиторий скачивается и вердикт возвращается так же, как для публичного.
2. **Given** URL приватного репозитория и отсутствие токена в окружении, **When** запущен анализ, **Then** система возвращает четкую ошибку о недоступности репозитория / отсутствии прав, без частичного результата.

---

### User Story 3 - Надёжная обработка сбоев и гарантированная очистка (Priority: P3)

Система работает с внешними зависимостями: сетевое скачивание репозитория и запросы к локальной LLM. Преподаватель должен быть защищен от «зависших» сценариев: при любой ошибке система либо повторяет временные сбои автоматически, либо возвращает четкую ошибку; при этом локальная копия репозитория гарантированно удаляется после завершения анализа — успешно или нет.

**Why this priority**: Надежность необходима для доверия к фиче, но не создает новой ценности сама по себе; она важна для эксплуатации, а не для первого прогона сценария P1.

**Independent Test**: Тестируется independently: имитируются недоступный репозиторий, сетевой сбой при скачивании и недоступная/некорректно отвечающая LLM. Проверяется, что в каждом случае возвращается понятная ошибка (а не валидированный, но «мусорный» результат), а временные данные удалены в любом исходе.

**Acceptance Scenarios**:

1. **Given** LLM временно недоступна или возвращает невалидный ответ, **When** запущен анализ, **Then** система автоматически повторяет запрос ограниченное число раз; если успех, возвращается вердикт, если нет — четкая ошибка.
2. **Given** репозиторий недоступен (неверный URL, не существует, нет прав), **When** запущен анализ, **Then** система возвращает четкую ошибку о невозможности скачивания репозитория.
3. **Given** любой прогон анализа (успешный или с ошибкой), **When** анализ завершается, **Then** локальная копия репозитория и все временные данные удалены: повторный запуск не накапливает артефактов.

---

### Edge Cases

- **Нет поддерживаемых файлов**: репозиторий не содержит ни одного файла с поддерживаемым расширением (например, только изображения или бинарники) — система сообщает, что анализируемого кода нет, и не выносит вердикт.
- **Пустая история коммитов**: репозиторий скачан, но не содержит ни одного не-merge коммита — анализ продолжает работу по коду, а в обосновании отражается отсутствие истории.
- **Merge-коммиты**: при анализе истории коммитов merge-коммиты исключаются (не считаются признаком и не искажают хронологию).
- **Неподдерживаемые расширения и служебные директории**: файлы вне белого списка расширений и содержимое служебных директорий (`.git`, `__pycache__`, `venv`, `node_modules`, `.idea`, `.vscode`) полностью игнорируются при сборе кода.
- **Превышение вместимости модели**: суммарный объем кода превышает возможности локальной LLM — система возвращает четкую ошибку, а **не** молча усекает код (усечение запрещено по заданию).
- **Сетевой сбой в середине скачивания**: прерванное соединение — обработка как ошибка скачивания с четким сообщением и очисткой временных данных.
- **Код без связи с критериями**: код решает общую абстрактную задачу, игнорируя специфические ограничения критериев — это обязательный фактор для «красного» статуса (см. критерии вердикта).
- **Повторный запуск без изменений**: повторный анализ того же неизмененного репозитория должен давать стабильный статус (детерминированность вердикта).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать на вход два параметра: текст критериев задания (произвольная строка) и URL репозитория с решением.
- **FR-002**: Система MUST скачивать полную локальную копию репозитория, включая всю историю коммитов, без использования API хостинг-платформы (лимиты запросов и пагинация не должны влиять на результат).
- **FR-003**: Система MUST извлекать полную историю коммитов: для каждого не-merge коммита — хеш, автор, дата (полный формат с временной зоной), сообщение.
- **FR-004**: Система MUST читать **полное** содержимое каждого файла с поддерживаемым расширением (`.py`, `.go`, `.rs`, `.js`, `.ts`, `.java`, `.cpp`, `.md`) без усечения и без «экономии токенов».
- **FR-005**: Система MUST исключать из сбора кода служебные директории: `.git`, `__pycache__`, `venv`, `node_modules`, `.idea`, `.vscode`.
- **FR-006**: Система MUST собирать метаданные репозитория (история коммитов, структура файлов) и исходный код **параллельно**, чтобы сократить общее время сбора данных.
- **FR-007**: Система MUST передавать на оценку локальной LLM одновременно: критерии задания, структуру файлов, историю коммитов и полный исходный код.
- **FR-008**: Система MUST возвращать структурированную оценку со следующими полями: статус (`green` / `yellow` / `red`), уверенность (число от 0.0 до 1.0), обоснование (развернутый аргументированный текст на русском языке), список признаков AI-генерации, список признаков человеческой работы.
- **FR-009**: Итоговая схема оценки MUST NOT содержать поле оценки соответствия кода критериям задания (`task_compliance_score` исключено).
- **FR-010**: Система MUST гарантировать удаление локальной копии репозитория и временных данных после завершения анализа — в том числе при любой ошибке на любом этапе.
- **FR-011**: Для приватных репозиториев система MUST поддерживать аутентификацию по токену, передаваемому через переменные окружения; токен не должен требоваться в URL или в конфигурационных файлах модуля.
- **FR-012**: При временных сбоях обращения к LLM (таймаут, ошибка разборa ответа) система MUST автоматически повторять запрос ограниченное число раз; только после исчерпания попыток — возвращать ошибку.
- **FR-013**: При неисправимой ошибке (недоступный репозиторий, отсутствие токена для приватного, LLM недоступна после всех повторов, нет поддерживаемого кода, превышение вместимости модели) система MUST возвращать четкую ошибку, а не частичный или невалидный результат.
- **FR-014**: Ввод для оценки MUST содержать четкие границы между отдельными файлами (путь файла + полное содержимое), чтобы LLM могла атрибутировать фрагменты кода конкретным файлам.
- **FR-015**: Система MUST присваивать статус вердикта по следующим критериям:
  - `green` (человек): постепенная история коммитов с осмысленными сообщениями; неидеальности и специфичные для задачи имена; код решает именно поставленную задачу с учетом её нюансов; комментарии по делу.
  - `yellow` (смешанный/подозрительный): код качественный, но история коммитов подозрительна (например, 1–2 коммита с разницей в минуту); избыточные «водянистые» комментарии в стиле ИИ при видимой попытке ручной адаптации под специфичные критерии задачи.
  - `red` (ИИ/копипаст): один коммит («initial commit»); идеальная, но бездушная структура; галлюцинации в комментариях; код решает общую абстрактную задачу, игнорируя специфические ограничения из критериев; артефакты нейросетей в коде или коммитах («Конечно, вот ваш код», «Sure, here is the solution»).

### Key Entities

- **Запись коммита**: хеш, автор, дата, сообщение; полная совокупность записей образует историю коммитов репозитория.
- **Файл исходного кода**: путь в репозитории + полное содержимое; принадлежит дереву файлов.
- **Дерево файлов**: полный список файлов репозитория (структура), передаваемый на оценку.
- **Оценка (результат детекции)**: статус (green/yellow/red), уверенность (0.0–1.0), обоснование на русском языке, список признаков AI-генерации, список признаков человеческой работы.
- **Задача (критерии задания)**: текстовое описание требований, с которым сверяется решение; передается на вход без преобразования.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полный анализ типового студенческого репозитория (до 20 поддерживаемых файлов кода) выполняется менее чем за 5 минут от начала до вердикта, включая скачивание.
- **SC-002**: 100% успешных анализов возвращают полный структурированный вердикт: статус, уверенность в диапазоне 0.0–1.0, обоснование и оба списка признаков — без отсутствующих или пустых обязательных полей (пустые списки признаков допустимы только при наличии их объяснения в обосновании).
- **SC-003**: На репрезентативном размеченном наборе репозиториев (чисто человеческие, чисто AI-сгенерированные, смешанные) не менее 80% репозиториев получают верный статус «Светофора».
- **SC-004**: 100% локальных копий репозиториев удаляется после завершения анализа, включая завершение с ошибкой: повторные запуски не накапливают временных данных.
- **SC-005**: Повторные (не менее 5) анализа одного неизмененного репозитория дают одинаковый статус вердикта не менее чем в 90% случаев (стабильность, отсутствие «прыжков» между категориями).
- **SC-006**: Временные сбои обращения к LLM (до 3 повторов) устраняются автоматически, без участия пользователя; устойчивый сбой приводит к четкой ошибке, а не к валидированному, но некорректному результату.
- **SC-007**: Анализ публичных репозиториев выполняется без какого-либо обращения к API хостинг-платформы и без авторизации на ней.

## Assumptions

- **Пользователь**: преподаватель или куратор курса, имеющий текст критериев задания и ссылку на репозиторий со студенческим решением; у него нет (и не требуется) личной авторизации на платформе.
- **Критерии задания** предоставлены уже готовым текстом; парсинг PDF/сканов критериев не входит в scope.
- **Среда выполнения** обеспечивает доступ к CLI-клиенту `git` (системная зависимость, заявлена в исходном ТЗ).
- **Локальная LLM** развернута и доступна модулю; модель поддерживает OpenAI-совместимый API и Structured Output (строго типизированный возврат).
- **Merge-коммиты** намеренно исключаются из анализа истории (заявлено в исходном ТЗ).
- **Дегенеративный случай «кода нет»**: репозиторий без поддерживаемых файлов — это ошибка с четким сообщением, а не вердикт.
- **Превышение вместимости модели** обрабатывается ошибкой, а не усечением: усечение кода запрещено исходным ТЗ.
- **Число повторов** при сбое LLM по умолчанию — 3 (разумный дефолт; точное значение настраивается).
- **Хранение результатов** (база данных, файлы, история проверок) не требуется: оценка возвращается вызывающей стороне в памяти; модуль без состояния.
- **Один репозиторий на одну проверку**: пакетный анализ (несколько репозиториев / студентов за один запуск) вне scope первой версии.
- **Язык вывода**: обоснование и списки признаков — на русском языке.
- **Вердикт не является окончательным решением** о списании студента — это инструмент поддержки решения преподавателя; допуски LLM не несут юридической силы.
